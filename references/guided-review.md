# 导览式验收：带用户逐节点过架构图

阶段 2（模块划分）收尾时的验收方式。源自 soc-demo 实践（2026-09-04）：用户不读长文档验收，而是"被带着走图"。

## 为什么

接口卡 + 架构图一次性丢给用户，内容太多看不完、也不知道看哪。验收质量取决于用户真的看懂了——所以要**导游式**：一次只讲一个节点，讲透再走。

## 机制（soc-demo 已实例化，可直接照搬）

- **真源与投影**：`specs/modules.md` 是唯一真源，图是它的投影——阶段 2 内模块卡一变，重出图再续导览；编码期以卡为准，图不强制同步，阶段 7 体检时刷新。
- **架构图节点可点击跳转详情页**：`docs/arch-notes.json` 存每个节点的注解（标题 + HTML body），`scripts/inject-arch-notes.mjs` 负责两件事——从 JSON 生成 `docs/nodes/<id>.html` 详情页、往主图 HTML 注入点击跳转逻辑（幂等，标记注释识别旧块）。
- **archify 重新 deliver 主图后必须重跑注入脚本**（deliver 会覆盖 HTML）。
- 详情页带"返回主图"链接；有内部结构图的节点挂延伸阅读链接。
- 注解内容的写法：真实世界对应物 → 干什么 → 接口/seam/验收要点。用 `CONTEXT.md` 术语。

## 带看纪律

1. **一次一个节点**，按主路径从左到右（告警源 → 接入 → 案件后端 → …）。
2. 大白话讲：先讲这个框在真实世界里是什么（比喻优先），再讲它干什么、刻意不干什么。
3. **不催进度**：讲完停下等用户提问；用户说"继续"才走下一个节点。绝不在结尾扔"下一步去哪"的催促。
4. **用户提问产生的决策当场落盘**：改 PRD 变更记录 + modules.md 对应卡 + CONTEXT.md（如涉及术语）+ arch-notes.json（如影响弹窗内容）——四处同步，不留口头决议。
5. 内部结构图的默认策略（2026-09-04 修订）：**地基/枢纽类模块默认主动画**（判定：有 ≥3 个内部件、或是全系统依赖起点，如案件后端的状态机+审计拦截+outbox）；普通叶子模块仍是用户点名才画。图画法：archify，含技术栈/部署/铁律三卡，产物挂到节点详情页的延伸阅读。图多了没人看，但地基没图讲不透。
