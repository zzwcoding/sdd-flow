# 功能 Spec 与模块接口卡模板

阶段 3 的产出格式。spec 是人和 AI 之间的合同：人审 spec，AI 按 spec 实现，测试验证 spec。

## 功能 Spec：`specs/<功能名>.md`

```markdown
# <功能名>

状态: 草稿 | 已定稿 | 实现中 | 已完成
来源: <PRD 章节或 issue 链接>

## 目标
<一句话：这个功能让用户/系统能做什么。用 CONTEXT.md 的术语。>

## 不做什么
<明确排除的范围，防止 AI 自由发挥扩大战果。>

## 触及的模块
| 模块 | 改动类型 | 说明 |
|---|---|---|
| <模块名> | 改实现 / 改接口 / 新增 | <一行说明> |

> 凡让 modules.md 卡的公开接口清单发生变化的（新增 / 变更 / 废弃），一律先回阶段 2 更新 `specs/modules.md` 并获得用户确认；spec 的接口定义节只做本功能视角的引用与细化。

## 接口定义
<本功能新增/变更的公开接口：签名、类型、错误情况。这是本 spec 最重要的部分。真源在 modules.md 卡——此处只做本功能视角的引用与细化，两处不一致以卡为准。>

## 行为约定
<输入 → 输出的具体规则，含边界情况和错误处理。每条用可判断真伪的陈述句。>

## 验收测试

| 验收标准 | 对应测试 |
|---|---|
| 给定 X，调用接口 Y，期望 Z | `tests/foo.test.ts::用例名` |

每条验收标准绑定一个测试标识（反引号包住）。测试标识三种合法写法：`用例名` / `路径::用例名` / `路径`。实现阶段逐一变成真实测试；spec 标 `已完成` 前，spec gate 会去源码里核实它们真的存在。

## 依赖与风险
<依赖的外部服务/其他功能；已知风险。>
```

## 模块接口卡：`specs/modules.md` 中每个模块一节

```markdown
## <模块名>

职责: <一句话>
目录: <代码所在目录>

### 公开接口
<签名/类型清单——调用方需要知道的一切，半页纸以内>

### 依赖
- 模块: `<模块a>`、`<模块b>`   ← 本仓库模块，反引号包住，供 spec gate 提取做无环与拼写校验
- 外部: <外部服务及其 adapter>   ← 不参与依赖校验

### Seam 与测试
- Seam: <本模块与外界的接缝位置>
- Adapter: <测试替身方案，如 FakeClock / InMemoryStore>
- 测试计划: <要锁死哪些行为>
```

## 机器可校验约定（spec gate）

以上格式不是审美偏好，是 `tools/check_specs.py` 的解析契约（脚本来源：sdd-flow `references/spec-validator.py`，零依赖，python3 直接跑）：

- `specs/modules.md`：`## 模块名` 即模块卡，卡内须有 `目录:` 行；`### 依赖` 下的 `- 模块:` 行提供依赖边。校验：依赖无环、依赖指向已声明模块、目录存在性（目录不存在仅警告，规划中的模块合法）。
- 功能 spec：`状态:` 行取值限 草稿/已定稿/实现中/已完成；`## 触及的模块` 表首列必须是 modules.md 里声明过的模块；`## 验收测试` 表每行"对应测试"列至少一个反引号测试标识；**状态 `已完成` 时测试标识必须能在源码中找到**——状态流转表的最后一挡由此获得机器守门。
- `.scratch/` 本地票：`Touches modules:` / `触及模块:` 行中的模块必须已声明（有该行才校验）。
- `docs/prd.md`：`状态:` 行取值限 粗稿/逼问中/已定稿；标 `已定稿` 时全文不得残留 `[待确认]`。缺状态行仅警告（兼容早期文档）。
- 票完成态：`Status: done`（验收框全勾、L0 核对回写后由总窗口置位）。spec 标 `已完成` 而相关票仍非 done → 警告（票与 spec 未必一一对应，只警告不拦截）。
- 跳过规则：`specs/` 不存在 → 整体跳过（阶段 0 CI 先行不被挡）；有功能 spec 但无 modules.md → FAIL（回阶段 2）；草稿状态的 spec 只查格式，不查表和测试存在性。
- 表格必须紧跟其标题（可隔空行），表头行自动忽略。

## 写作纪律

- 用 `CONTEXT.md` 的术语；术语不存在就先补术语表，不要现场发明同义词。
- 接口定义写给"不了解实现的调用者"看；写完自查：只看接口能正确使用吗？
- 行为约定写"可测试的陈述"，不写"应该尽量快"这类无法判断的话。
- spec 有漏洞时不许在代码里猜——回阶段 1 补逼问或回阶段 3 改 spec。
- spec 定稿前先跑 `python3 tools/check_specs.py`——机器校验先于 L0 人审，别让人替脚本干活。
