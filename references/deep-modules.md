# 深模块划分准则

阶段 2（模块划分）的判断标准。源自 John Ousterhout《A Philosophy of Software Design》，经 Matt Pocock 适配到 AI 编码场景。

## 核心概念

- **模块（module）**：应用中一个职责单元。一个功能块、一组相关组件、一个服务。
- **接口（interface）**：调用者正确使用该模块所需知道的一切——公开签名、类型、以及必要的使用约定（文档）。接口是人对模块施加品味的地方。
- **实现（implementation）**：接口背后的一切。实现委托给 AI，测试锁死后不用关心内部。
- **深模块**：少量接口隐藏大量实现。**浅模块**：接口复杂但背后没多少实现——是要消灭的反模式。
- **depth（深度）**：调用者每学一单位接口，能驱动多少行为。深度是划分模块的第一标准。
- **seam（接缝）**：模块间接口所在的位置。测试打在 seam 上；需要替换实现时也在 seam 上（配 adapter，如真实时钟 vs 假时钟）。
- **locality（局部性）**：一个关注点的改动集中在一处。给维护者的收益。
- **leverage（杠杆）**：调用者学一点接口获得很多能力。给调用者的收益。

## 划分步骤

1. 从 PRD 列出所有功能块，按"天然会一起变化"聚类。
2. 每一簇候选为一个模块，先写它的**公开接口草案**（签名 + 一句话语义），不写实现。
3. 对每个候选问三个问题：
   - 接口是否明显比实现简单？（是 → 深；否 → 浅，合并或重划）
   - 改动这个关注点时，是否只会动这一个模块？（locality）
   - 调用方是否不用看内部就能用对？（leverage）
4. 模块间画出依赖方向，确认无环；任何跨模块调用只能走对方公开接口。
5. 标出每个 seam 需要的 adapter（外部服务、时钟、随机数、存储——一切测试时要替换的东西）。

## 验收清单（划分完成的标准）

- [ ] 模块数量是人脑能装的量级（7±2 个一组，超出就再聚合成层）
- [ ] 每个模块接口能用半页纸写完
- [ ] 文件系统结构 = 模块结构（一个模块一个目录，接口文件在目录最显眼处）
- [ ] 没有浅模块
- [ ] 依赖无环
- [ ] 每个 seam 有测试计划，外部依赖有 adapter 方案

## 反模式（看到就返工）

- **浅模块瘟疫**：几十个小文件互相 import，每个只导出一两个小函数。合并成深模块。
- **跨模块顺手 import 内部文件**：绕过接口拿实现细节。用 CI 边界检查禁止。
- **接口泄露实现**：返回类型里带着内部结构、参数要求调用方了解内部状态。
- **并行重复实现**：同一概念两处实现且接缝处无测试。合并为一个模块。
- **为拆而拆**：三行代码的 helper 不配独立成模块。

## 与人的分工

人（战略层）：决定模块边界、设计接口、审 `specs/modules.md`。
AI（战术层）：写模块内部实现、写 seam 处测试、在接口约束内自由发挥。
